## 现象

旧循环用 abortable 在收到取消信号时立即结束模型等待，没有等待传输资源实际退出的屏障。即便 driver 本身在 complete 结束前等待连接 close，外层也可能先结束回合、释放会话所有权。

## 复现步骤

1. 仅启动自建回环 HTTP 假模型，让其保持 SSE 连接。
2. 使用实际自有 API driver 和临时数据库创建回合，在 waitForIdle 增加受控收尾门闩。
3. 取消请求，要求连接实际关闭后仍等待门闩，期间状态保持 running、新回合被拒绝。
4. 同一回归针对提交前 HEAD 的 turn-engine 运行，因 waitForIdle 从未调用而失败；恢复修正源码后通过。临时源码替换与恢复在同一脚本 finally 完成，没有并发运行其他检查或使用真实服务。

## 影响

正式网络接入后可能使新回合与尚在收尾的旧请求短暂重叠；迟到结果隔离不等于资源生命周期结束。本次仅回环假接口和临时状态，独立正式任务仍关闭，无真实模型或计费。

## 根因

取消信号触发外层 Promise 的拒绝早于底层 complete 的最终收尾，旧接口只有信号、没有资源收尾接缝。

## 处理方式

protocol 可选追加 waitForIdle；实际 API driver 跟踪任务请求，等待客户端连接 close 后 settle。循环捕获取消后先等待该方法，再保存终态并释放所有权。旧无此方法的假 driver 仍只保留迟到隔离，不扩大保证。

## 验证

旧 HEAD 反例退出码 1、未超时，确因 waitForIdle 未调用失败；修正后同例及当前三协议定向测试通过。最终全量检查和修复提交完成后追加哈希。
