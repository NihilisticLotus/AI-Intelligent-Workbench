# ISSUE-0046：会话内切换被拒绝后缺少失败模型标记

## 现象

已有会话切换到列表中的另一个模型，上游 set_config_option 明确拒绝。界面正确报错并保留原模型，但再次打开选择器没有“上次失败”，和 phase-1 9.6 的记录要求不一致。默认模型在会话建立后能被实际配置回写，本次没有证据支持“默认模型失败一定记为空名”的初始疑点。

## 复现步骤

1. 用仓库假 ACP 进程配置 alpha / beta，第一次纯文本回复成功；不启动真实 Agent、不访问外部服务。
2. 对 model:beta 返回 -32602，网页选择 beta。
3. 基线定向回归：任务保留 alpha，但 model_failures 查询返回 undefined，期望 beta / 实际账号失败；模型列表没有相应记录。

## 影响

用户会反复选择已被拒绝的模型，工作台失去按账号提示失败历史的作用。

## 根因

TaskService 只在 runTurn 的 AgentError 分支写入 model_failures。会话内 switch 的 setConfig 异常分支只回写原配置、重新抛错，没有记录模型拒绝。

## 处理方式

仅在请求了不同模型、AgentError.reason=invalid_value、且 Agent 返回的实际模型没有变为所请求模型时写失败记录，使用运行会话的账号并发布 agent.status。继续保留原值与错误提示，不自动重发。模型已经生效但随后思考强度被拒绝，以及额度错误均不标记模型不支持。无协议、迁移、依赖或第三方配置变化。

## 验证

- 新增四项真实形态假 ACP 集成测试：默认模型正文拒绝的暂停 / 原文 / 实际账号和模型、会话内拒绝切换、模型已生效后的强度拒绝不污染、额度正文不污染。
- 修复前会话内失败标记断言失败；修复后四项通过，typecheck / build 通过、默认 712 项通过 / 3 项真实冒烟跳过。
- 17891 独立数据夹具的实际浏览器操作：选择 beta 被拒绝、仍为 alpha / low，再打开选择器显示“上次失败”及原因；只有一条假 ACP 消息，无工具、无真实模型或外网调用。截图和摘要见 step-1.3 最新节。
- 真实供应商拒绝模型仍未验证，不用本机夹具替代 ISSUE-0023 的真实证据。
