## 现象与复现

旧 AttachmentService.read 调用 get / exists 后直接按路径 readFileSync，没有拒绝目录联接 / 硬链接、写占用或核对上传大小 / 摘要。仅用本机临时无密钥夹具：上传后移走任务附件目录，改为指向另一个临时目录的联接，其中同名文件改为外部夹具文本。

从 HEAD 提取旧 read 方法原始函数体，仅替换该临时 Gateway 实例的方法；通过已认证下载接口实际得到 200 和外部夹具文本。finally 恢复当前实例后，同一请求得到 409 attachment.read_failed。没有覆盖生产源码、读取真实凭据或用户外部文件，也没有把夹具正文写进输出。

## 影响与根因

设备认证不能证明附件文件仍属于原上传。已获本机修改权限的进程替换磁盘路径后，下载接口仍会把另一份内容当原附件返回；独立模型不能沿用此普通读取作为安全输入。此验证不证明远端网页能够直接修改本机目录。

## 处理方式

下载与模型共同使用任务数据库快照、Windows 固定目录 / 文件句柄、单链接和写占用检查，先限大小再读，同一读取核对上传摘要，回传后复核快照。正文只经私有管道，失败统一固定错误；关闭服务取消等待与活动作业。原生 Agent 的文件 URI、上传 / 删除路径机制以及任意命令系统隔离不在本单证明范围。

## 验证

四项 HTTP 回归覆盖摘要、大小、目录联接、硬链接，均要求固定 409、不含路径 / 外部正文，错误 Host / Origin 仍 403；实际附件定向 19 项含双层联接、硬链接、写占用、持锁宿主取消 / 关闭和三协议回环。网页既有图片缩略图与大图可正常查看。最终全量检查与修复提交随后追加。
