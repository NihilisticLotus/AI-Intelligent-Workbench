## 现象

候选发行包 `@earendil-works/pi-agent-core` / `pi-ai` 的 `1.5.0` 行为不能直接映射成工作台的执行与统计结果：

- 工具 schema 要求字符串时，原始数字 `123` 可被转换为字符串后执行。
- 异步 `tool_execution_start` 订阅抛出持久化错误时，工具确实未执行，但 `prompt()` 正常返回，并通过助手的 `stopReason: error` / `errorMessage` 表达失败；该中断位置的工具结果不会自动补齐。
- Chat 流未报告 usage 时，归一化结果仍有零值，不能据此把未报告显示为实际零消耗。
- 不完整模型对象缺少 `baseUrl` 时，直接 Chat 适配器会同步抛 TypeError，不能只处理流里的错误。
- Messages 适配器发往显式服务的路径会附加 `?beta=true`；不代表任意第三方兼容服务接受该参数。

这些是已观察到的依赖契约和接入限制，不据此宣称上游实现有 bug。

## 复现步骤

1. 在工作台忽略目录准备上述固定版本及 `pi-schema@1.5.0`，禁用安装脚本；项目自身依赖不变。
2. 运行开发验证脚本 `scripts/dev/verify-independent-agent.mjs`。脚本只加载隔离目录中的候选包，用假模型、假 Key、模拟流和临时文件验证。
3. 查看关于参数转换、记录失败、缺地址、缺 usage 和 Messages 的特征测试；对照[结构化证据](../acceptance/assets/step-1.3-independent-poc.json)。不使用真实认证或服务。

## 影响

若只以 Promise 是否拒绝判断成功、依赖 SDK 的参数转换，或直接把归一化零值送入费用界面，会错误执行、误判终态或误导用量。记录失败后的工具配对仍须宿主恢复；不能原样发送不完整历史。兼容服务必须验证实际请求路径和参数。

## 根因

SDK 负责模型与循环层，其允许转换的参数校验、消息错误契约与默认 usage 结构不同于工作台的严格边界和未知状态。它不负责 Gateway 事务、恢复与产品计费语义。具体行为已通过安装发行包的源码与离线场景核对。

## 处理方式

若继续采用 Pi：在审批与执行前严格校验原始工具参数；所有入口同时处理同步异常和流错误；以终态判断成功；将调用意图和结果可靠持久化，恢复时补齐中断工具结果且不自动重放副作用；用原始协议事件另记 usage 是否报告；请求路径和 beta 参数按服务明确适配。示例保护已在验证脚本中证明可插入，正式适配层尚未实现。

若后续离线门槛不能满足，重新评估候选或自建；不能为采用 SDK 放宽要求。未确定最终依赖，不修改上游包，不开放真实调用。

## 验证

27 项离线验证通过，其中包含暴露默认语义的特征测试及部分宿主保护示例。正式接口、数据库、界面、崩溃恢复、Windows 命令取消、真实服务兼容均未验证；本问题保持调查状态，不以脚本通过作为正式修复。
