# 文档与记录：放在哪、怎么写、怎么溯源

目的：半年后任何人（包括另一个 AI Agent）都能回答“这个功能为什么这样做、什么时候改的、当时遇到过什么问题、怎么验证的”。

## 1. 存放位置

所有文档都在 `docs/` 下，只有这七个子目录：

| 目录 | 放什么 | 写法 | 能否修改旧内容 |
|---|---|---|---|
| `docs/design/` | 架构设计 `design.md`、界面设计 `ui-design.md` | 描述“现在应该是什么样”，随决定更新；在开头写版本号和变更摘要 | 可以，但重大改动要在 devlog 里留记录 |
| `docs/research/` | 调研报告 `<topic>.md` | 写明日期和来源；结论经过核查的要注明 | 只更正错误，标“更正”；过时的另写新报告 |
| `docs/plans/` | 开发计划 `phase-<n>.md` | 阶段、步骤、完成标准 | 可以，范围变化在 devlog 里记录原因 |
| `docs/prototype/` | 可点击的界面原型 | 双击 `index.html` 打开 | 可以 |
| `docs/acceptance/` | 每一步的验收记录 `step-<x.y>.md`，证据放 `assets/` | 用模板；写实际做过的验证 | 不改旧记录；重新验收就追加一节 |
| `docs/devlog/` | 开发笔记，每月一个文件 `YYYY-MM.md` | 按时间追加：做了什么决定、为什么、关联的提交 | 只追加，不改写历史 |
| `docs/issues/` | 问题收纳：`README.md` 是总表，每个问题一个文件 `ISSUE-<4位编号>-<slug>.md` | 用模板；状态变化追加到“时间线” | 只追加时间线，不删问题单 |

`docs/README.md` 是文档总目录，新增文档时一并更新。

## 2. 开发笔记（devlog）

- 每条笔记一个小节：`## 2026-11-06 自动交接改为默认无弹窗`。
- 内容：背景（谁提出、什么现象）、决定、放弃了哪些方案及原因、影响到的文件，以及关联的提交和问题单。
- 用户的决定要原话或准确转述，并注明“用户决定”。例如“快速判断默认引擎：已有账号的便宜模型（用户决定）”。
- 写笔记的时机：做了需要解释的选择、改变了计划、推翻了之前的设计。纯粹的执行不用写。

## 3. 问题收纳（issues）

- 什么要记：bug、验收没通过、外部依赖的坑（例如某个 Agent 在 ACP 模式下忽略 MCP）、暂时绕过去的问题、以后要做但现在不做的事。
- 编号从 `ISSUE-0001` 递增，永不复用。总表 `docs/issues/README.md` 每个问题占一行：编号、标题、状态、类型、开启日期、关闭日期。
- 状态：`open`（新建）→ `investigating`（调查中）→ `fixed`（已修复，附提交）/ `wontfix`（不修，附理由）/ `deferred`（推迟，附目标阶段）。
- 问题单包括：现象、复现步骤、影响、根因、处理方式、验证、时间线。修复提交的“关联”一行写上编号，问题单的时间线里写上提交哈希，双向可查。
- 关闭不等于删除：已关闭的问题单永久保留。

## 4. 验收记录（acceptance）

- 每一步（如 1.1）完成时写一份。内容：完成标准逐条打勾、实际操作步骤、测试命令与结果、截图（放 `assets/`）、没通过和没验证的项（同时开问题单）、对应的提交范围。
- 只写真实做过的验证。没做的写“未验证”，不许写“应该没问题”。

## 5. 互相引用

| 从 | 引用 |
|---|---|
| 提交正文 | 问题单编号、devlog 日期、验收文件 |
| 问题单 | 发现它的验收记录、修复它的提交哈希 |
| devlog | 相关的提交哈希、问题单、设计文档章节 |
| 验收记录 | 提交范围（起止哈希）、遗留问题单 |
| 设计文档 | 做出该决定的 devlog 日期 |

## 6. 不要做

- 不在代码目录、根目录或 `.agent/` 里放笔记和问题记录。
- 不用“最终版”“新版2”之类的文件名；需要版本就写在文件内容里。
- 不删除历史记录来“保持整洁”，整洁靠目录结构，而不是删东西。
