## 现象

自有服务使用用户在界面保存的凭据、Responses 和 glm-5.3。首条文本对话成功；第二条请求创建临时文件时，第一次生成的 write_file 参数为 {}，被宿主严格校验拒绝。循环将工具错误返回模型后，下一次生成以 protocol 失败结束。没有出现待批准卡片，文件没有创建。

## 复现步骤

1. 在 Agent 页添加独立 Responses 服务，基础地址使用用户指定的智谱地址，手动录入 glm-5.3 与文档能力；不修改第三方 Agent。
2. 新建只含合成项目规则的临时项目，需审批权限，low、流式、输出 2048、本地输入估算上限 16000；设置任务请求上限 12、CNY 人工预留 5 元、每次 0.4 元。
3. 发送记住暗号并复述规则的消息，成功后请求用 write_file 创建 real-proof.txt。
4. 只读取已有原始记录与请求账本核对，不自动重发。

## 影响

本轮只能确认独立真实文本链路，不能确认文件批准 / 拒绝、换模型、视觉、取消或恢复。共 2 条用户消息、3 次生成 POST，已占 1.2 元人工预留，第三次 usage 与全部实际账单未知；失败不退额度。已按预算停止后续真实调用。

## 根因

未查明。持久助手私有续传中的 function_call.arguments 也是字符串 {}，排除仅网页展示漏参。代码检查发现 write_file 的 Zod 联合导出为顶层 oneOf，宿主再加 type: object，没有顶层 properties；这是兼容疑点，尚未证明智谱忽略此 schema，不能据此断言供应商或模型缺陷。第三次失败只有固定 protocol 诊断，没有完整终态证据，不能推断具体缺哪个字段；不为排查放宽签名、工具或用量校验。

## 处理方式

保留原协议、模型、能力与全部请求记录，不切接口 / 服务兜底，不读取第三方凭据。先完成离线核对；进一步真实诊断须遵守原停止约定，明确新增请求用途并沿用剩余额度，不清空累计次数。不得把局部工具错误后的模型修正续传漏记为免费或传输重试。

- 工作台原始记录：工具名 write_file，参数 {}；工具结果为“工具名称或参数不符合严格规范，未执行”。
- 只读持久库：请求 1 / 2 succeeded，请求 3 failed / protocol；无 reserved；real-proof.txt 不存在。
- 未验证：原因对应的完整上游终态、修复后的真实工具流程、Flash 图片、实际供应商费用。
